# FmJev

[日本語版 / Japanese](README.ja.md)

A local Jev-style HTTP API powered by Apple's `fm respond`. The Python environment is managed with `uv` and uses Python 3.14. There are no third-party Python dependencies. A working `fm` installation is required.

## Getting started

```sh
cd fmjev
uv sync --locked
fm available
fm respond --no-stream 'Reply with hello.'
uv run --locked python -m fmjev
```

The server listens on `http://127.0.0.1:8080`. Press Ctrl+C to stop it.

```sh
curl -sS http://127.0.0.1:8080/health
curl -sS http://127.0.0.1:8080/v1/systemone \
  -H 'Content-Type: application/json' \
  --data-binary @examples/request.json
```

`GET /health` checks server liveness only; it does not guarantee that inference will succeed.
Change the port and timeouts with `uv run --locked python -m fmjev --port 8081 --timeout 60 --request-timeout 180`.
Use `--fm ./path/to/fm` to specify the executable.

## Requests and responses

`POST /v1/systemone` accepts JSON containing `state` and `questions`. The `model` field is optional; if supplied, it must be `fmjev-fm`. The API rejects `jev-latest` to avoid confusion with the actual Jev model.

```json
{
  "state": "Please refund my purchase.",
  "questions": {
    "refund": {
      "type": "noul",
      "instructions": "Is the customer requesting a refund?"
    }
  }
}
```

Example response shape (values are illustrative):

```json
{
  "model": "fmjev-fm",
  "answers": {"refund": {"type": "noul", "noul": 0.95}},
  "metadata": {
    "backend": "fm",
    "probability_method": "model_self_report",
    "calibrated": false,
    "confidence_method": "1 - normalized_shannon_entropy",
    "question_execution": "isolated_sequential",
    "elapsed_ms": 1000
  }
}
```

| Question type | criteria | Fields in each answer |
| --- | --- | --- |
| choice | Object mapping option names to descriptions; 2–255 options | choice, probabilities, confidence |
| score | Array of level descriptions ordered from low to high; 2–10 levels | score, probabilities, confidence, legend |
| noul | Omitted, or descriptions keyed by true and false | noul (estimated probability of yes) |

`instructions` accepts a string, object, or array. Each description in `criteria` accepts these types or null.
Score levels start at 0, and `score` is their probability-weighted mean. Choice selects the option with the highest probability; ties go to the option declared first in the input.

## How fm is used

Each question starts an independent `fm respond --no-stream --schema ... --instructions ...` call.
The state and question are passed through standard input without invoking a shell. Question IDs are not sent to the model.
Candidate fields in the schema are mapped internally to `p0`, `p1`, and so on, while option names and descriptions are supplied in the prompt.
The code restores the original option names after generation, so returned choices are limited to the input options.
Schema files are created in temporary directories and deleted after each call. Inputs, responses, and keys are not saved to files or access logs.

Probabilities must be finite numbers between 0 and 1. They are normalized only when their sum differs from 1 by at most 0.05. Larger discrepancies or an all-zero distribution return HTTP 502. There are no automatic retries.

## Differences from Jev

- The main request and `answers` structures follow Jev's API. This is not a fully compatible API or SDK replacement.
- Probabilities are numbers generated by the model. They are uncalibrated and are not token probabilities.
- Confidence uses the custom definition `1 - H(p)/log(n)`: 0 for a uniform distribution and 1 for a distribution concentrated on one outcome. It measures concentration, not accuracy, and may differ from Jev's confidence.
- Questions run **sequentially in independent sessions**. Adding questions or options increases processing time and context usage. This does not reproduce Jev's parallel inference performance.
- The API does not return `usage`, because exact token usage is not collected.
- The API does not perform automatic evaluations or call the external Jev API. `TYPESAFE_API_KEY` is not required for local operation.

## Limits and errors

This server is intended for local prototyping and binds only to 127.0.0.1. It has no authentication and does not enable CORS. It is not intended for public deployment.
Requests are limited to 256 KiB and 32 questions. Only one inference request runs at a time; additional requests receive HTTP 429 while it is running.
Large inputs can still fail within these limits because of the model's context limit.
The default timeout is 60 seconds per question and 180 seconds for all questions combined. If a request fails partway through, no partial answers are returned.

| HTTP | Meaning |
| --- | --- |
| 400 | Invalid JSON or question definition |
| 411 / 413 / 415 | Missing Content-Length / body too large / unsupported Content-Type |
| 429 | Another inference request is running |
| 502 | Invalid fm output |
| 503 | Could not execute fm, or inference failed |
| 504 | Inference timed out |

Error format: `{"error":{"code":"invalid_request","message":"..."}}`

`ModelManagerError 1008` can occur even when `fm available` succeeds. In this development environment, inference failed inside the sandbox but succeeded when the same command was run outside it with permission. Try the minimal inference command above in a regular terminal.

## Tests

```sh
uv run --locked python -m unittest discover -s tests -v
```

Unit and HTTP tests use a fake backend and do not require a model. To check actual inference, start the server and POST `examples/request.json`.

### Actual model check (2026-09-17)

The Japanese example was submitted over HTTP, and all three questions completed in about 2.3 seconds. Choice returned `returns`, Score returned `0.7`, and Noul returned `0.8`.
However, the input explicitly requested an exchange rather than a refund, so `noul: 0.8` for refund intent was incorrect. Adding instructions emphasizing negation did not resolve that error in this run.
This check confirms that the API connects to the actual model; it does not establish decision accuracy. Japanese negation and numerical probability estimates in particular need evaluation for each intended use case.
